三、三项新方法论具体写了什么

3.1 headers：请求头 + 敏感值不入库

"headers": {"Cookie": "${MYSITE_COOKIE}", "Referer": "https://www.example.com/"}
  • 值支持 ${VAR} 占位符，可与环境变量混着写普通值（如上面的 Referer）。
  • 变量未设置 → 该请求头被省略并打印告警，不会发空值、也不会静默成功。
  • 本机来源 src/local_secrets.json（必须 gitignore），云端来源 Actions Secrets； setdefault 语义保证已有环境变量不被文件覆盖。

3.2 cookie_recovery：失效自愈（写明是尽力而为）

"cookie_recovery": true,
"cookie_name": "cdndefend_js_cookie",
"cookie_wait": 4

链路：带 headers 直连 → 失败或结果无效（挑战特征 或 解析 0 条）→ 浏览器过挑战取该名称 cookie → 换头重连一次 → 仍失败则跳过并保留旧 feed。

文档里明确写了局限，没有包装成「保险」：自愈成立需要两个前提——浏览器还能真正过挑战、且它铸出的新 cookie 能被 urllib 复用。这两个前提都可能不成立，实测反例见第五节。

3.3 字段级 base：图片在独立域名时必须分开配

"base": "https://www.example.com",
"fields": {
  "link":   {"pattern": "href=\"(/movie/[^\"]+)\"", "group": 1, "abs": true},
  "poster": {"pattern": "data-original=\"(/vod\\d+/vod/[^\"]+)\"", "group": 1, "abs": true,
             "base": "https://vres.example-cdn.com"}
}

字段自带 base 时覆盖源级，不填则回落源级——不配的源行为与旧版完全一致。 文档同时写了两条配套判据：① 用 curl -I 逐域名试同一相对路径，200 且 content-type: image/* 的才是对的； ② 真实图片常在 data-original/data-src，只匹配 src 会得到「条目数对、海报全空」。

五、验证中发现的真问题（推翻了我此前一个结论）

上面自愈那步这次失败了。查证后确认不是代码写错，而是站点侧发生了变化：

时间浏览器铸出的 cookie用 urllib 直连回放
~17:0075CB7DA5…A14423200 / 24 条，此后一小时反复可用
~17:401B23136A…6624HTTP 850；同会话 ctx.request.get() 也是 850

同期浏览器自身也只拿到 1616 字节空白页（不再有 24 条），说明那个新值根本不是「通过挑战后的通行证」。 而一小时前铸出的旧值仍然有效。

结论修正：cookie 不是永久静态值，会随时间轮换，且新铸出的值不一定能用于直连。 因此 cookie_recovery 只能算「减少人工干预」，不能当成「这个源不会断」的保证。 真正可靠的判断标准只有一条：拿这个值请求一次，200 且页内有条目（只看状态码不行，850 也是有响应的）。

这条修正已一并回写到你项目的 README.md 与 report/kkys14_probe_and_fix.html （原文写的是「静态值」「自愈已验证」），避免以后按错误前提排错。
